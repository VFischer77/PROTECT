# PROTECT Q02 v0.2 — Consolidated CAPA Design Review

Status: PROPOSED — owner acceptance pending. Design only, no executable software or tests performed.

## Q02.1 Scope and lifecycle
Q02 is an analytical module, not an eQMS or CAPA workflow replacement. Client retains responsibility for approvals, CAPA closure, effectiveness determinations, source records and product decisions.

Lifecycle: (1) initiation/source/rationale (2) root-cause alignment (3) action planning and proportionality (4) implementation (5) effectiveness verification (6) post-verification monitoring (7) management evaluation.

## Q02.2 Logical data groups
CAPA identification/site/process/source; initiation trigger/date/source classification; investigation and root-cause linkages; action plan, responsible functions and original/revised due dates; implementation status and dates; verification method/acceptance criteria/date/client-approved outcome; linked subsequent events and chronology; management escalation. Fields must be specified as required, conditionally required or optional for each analytical use. Missing evidence does not imply favorable status.

Inherit the workspace-level Industry and Service Domain profile configured once at PROTECT initialization (GC-001); Q02 does not present module-level selectors. Apply CC-01–CC-30 according to relevant sector, module, event and jurisdiction. Preserve client classification separately; no default to None for unclassified.

## Q02.3 Proposed indicators
CP-01 initiation timeliness; CP-02 root-cause alignment; CP-03 CAPA plan adequacy; CP-04 implementation timeliness; CP-05 overdue burden; CP-06 implementation completeness; CP-07 verification adequacy; CP-08 effectiveness outcome; CP-09 post-CAPA contextual recurrence; CP-10 reopening/rework; CP-11 systemic coverage; CP-12 management response. Independent indicators; no unvalidated composite score.

Client-approved effectiveness: Effective / Not Effective; Pending if not verified. Never conflate completion with effectiveness. Pending excluded from conclusive effectiveness denominator. Define counting populations, many-to-many links, original vs revised due dates, and low-volume safeguards before implementation.

## Q02.4 Contextual recurrence and integration
Use shared ABI-REC-001, not another recurrence engine. Evaluate root cause, failure mechanism, operating context, CAPA intended scope, chronology, and evidence strength. Similar words are not proof; different terms can describe the same mechanism. Post-verification related events trigger contextual reassessment without overwriting client-approved outcomes. Absence of recurrence alone is not proof of effectiveness. Link relevant Q01/Q03/Q04/Q05/Q06/Q08/Q09/O01 and broader Q/O/R/B/S/G modules as appropriate. Defer ABI-SYS-001 to later predictive integration.

## Q02.5 Proposed acceptance scenarios — NOT EXECUTED
CAPA-01 on-time yet ineffective; 02 root-cause misalignment; 03 different terminology/same mechanism; 04 same terminology/different mechanism; 05 event before implementation; 06 related event after effective verification (flag only); 07 pending effectiveness; 08 many-to-many CAPA/deviation no double count; 09 original and extended deadlines; 10 cross-site systemic coverage; 11 insufficient evidence; 12 time-respecting predictive baseline evaluation.
